# 사내 프로젝트 및 인사평가 관리 시스템 DB 설계 시나리오

## 1. 프로젝트 개요
이 프로젝트는 100명 규모의 SI 업체(마케팅/경영 30명, 개발자 70명)가 월평균 10여 개의 프로젝트를 수행하는 환경을 위한 **사내 프로젝트 투입 및 인사평가 관리 웹 기반 시스템**의 데이터베이스 설계를 목표로 합니다.

## 2. 주요 비즈니스 요구사항 및 제약사항 (Business Rules)
요구사항을 바탕으로 다음과 같이 세부 비즈니스 로직과 데이터 규칙을 정의합니다.

*   **사번 규칙:** `EMP` + `입사연도(4자리)` + `일련번호(3자리)` 형태로 자동 부여됩니다 (예: `EMP2026001`).
*   **회원가입 및 계정:** 신규 직원은 웹페이지에서 ID 중복 체크 후 가입하며, 기술 스택(Skill Set)의 경우 다중값 속성(Multivalued Attribute)이므로 정규화를 거쳐 별도 테이블로 분리합니다.
*   **프로젝트 투입 (M:N 관계 해소):** '사원'과 '프로젝트'는 다대다(M:N) 관계입니다. 하나의 프로젝트에 여러 사원이 참여하고, 한 사원이 여러 프로젝트에 참여할 수 있으므로 브릿지 테이블(`Project_Assignment`)을 생성하여 1:N 관계로 해소합니다.
    *   **투입 직무 목록:** PM, PL, 분석자, 설계자, 프로그래머, 테스터
*   **프로젝트 평가 체계:** 프로젝트 종료 시 3가지 유형의 평가가 발생합니다. 평가는 업무수행(1~5점), 커뮤니케이션(1~5점), 주관식 평가 내용으로 구성됩니다.
    *   **고객 평가:** 고객사 담당자의 평가서를 PM이 대리 입력.
    *   **PM 평가:** PM이 프로젝트 팀원을 평가.
    *   **동료 평가:** 프로젝트 참여 팀원 간 상호 평가.
*   **권한 및 접근 제어 (RBAC):**
    *   **일반 직원:** 본인 정보 수정, 본인 투입 이력 조회, 진행 중인 프로젝트 동료 평가.
    *   **PM:** 담당 프로젝트 팀원 투입, PM 평가, 고객 평가 등록.
    *   **경영진:** 전사 직원 검색, 프로젝트 투입 현황 통계, 개인별 과거 투입 이력 및 인센티브 산출용 평가 결과 조회.

## 3. 핵심 엔티티 도출 (Entity Identification)
*   `Employee (사원)`: 사번(PK), 직원명, 주민등록번호, 최종학력, ID, Password 등
*   `Skill (기술)`: 기술코드(PK), 기술명 (예: Java, Oracle)
*   `Employee_Skill (사원_기술 보유)`: 사번(FK), 기술코드(FK), 숙련도
*   `Project (프로젝트)`: 프로젝트번호(PK), 프로젝트명, 착수일자, 종료일자, 발주처, 상태 등
*   `Project_Assignment (프로젝트 투입)`: 투입ID(PK), 프로젝트번호(FK), 사번(FK), 투입시작일, 투입종료일, 직무
*   `Evaluation (평가)`: 평가ID(PK), 프로젝트번호(FK), 평가자사번(FK), 피평가자사번(FK), 평가구분(고객/PM/동료), 업무수행평점, 커뮤니케이션평점, 상세내용

## 4. 데이터베이스 설계 핵심 포인트 (Database Design Focus)
강의에서 다룬 핵심 개념들을 설계에 적극적으로 반영합니다.

*   **무손실 조인 분해 (Lossless-Join Decomposition):** 테이블을 분해할 때 연결 정보가 상실되지 않도록 정규화를 수행합니다. 잘못된 분해로 인해 발생하는 'Connection Trap'을 방지합니다.
*   **제3정규형 (3NF):** 모든 속성이 기본키에 비이행적으로 종속(Non-transitively dependent)되도록 설계하여 이상 현상(Anomaly)을 최소화합니다. 의존성 보존(Dependency Preservation)을 고려하여 BCNF 대신 3NF 수준에서 정규화를 완료할 수도 있습니다.
*   **비식별자 관계 (Non-Identifying Relationship):** `Project_Assignment` 테이블 생성 시 `Employee`와 `Project`의 PK를 상속받아 복합키로 사용하면 식별자가 무한 증식할 수 있습니다. 이를 방지하기 위해 비식별자 관계를 적용하여 독립적인 투입ID(PK)를 생성하고 사번과 프로젝트번호는 FK로 참조합니다.
*   **다중값 속성 분리:** 사원의 기술 스택(Skill Set)은 한 직원이 여러 개를 가질 수 있는 다중값 속성이므로 별도의 `Employee_Skill` 엔티티로 분리하여 관리합니다.

## 5. 데모 시연 시나리오 (End-to-End Use Case)
발표 시 시스템의 핵심 가치를 보여줄 4단계 시나리오입니다.

*   **Scene 1: 신규 개발자 회원가입 (Developer View)**
    *   신규 입사자가 웹 시스템에 접속하여 사용할 ID 입력 후 중복 체크 수행 (실패 및 성공 케이스 시연).
    *   기본 정보 및 보유 스킬(Skill Set)을 다중 선택하여 가입 완료.
    *   *DB Point:* 사번 자동 생성 트리거(또는 로직) 확인, `Employee`와 `Employee_Skill` 테이블 간의 1:N 관계 및 데이터 저장 확인.
*   **Scene 2: 프로젝트 생성 및 인력 배치 (PM View)**
    *   PM이 신규 프로젝트를 등록하고, 개발자들의 투입 기간과 직무(프로그래머, 설계자 등)를 할당.
    *   *DB Point:* M:N 관계를 해소한 `Project_Assignment`(브릿지 테이블)에 데이터가 어떻게 비식별자 관계로 삽입되는지 시연.
*   **Scene 3: 프로젝트 종료 및 평가 입력 (Evaluation)**
    *   프로젝트 상태를 '종료'로 변경 후, PM이 고객 평가서 대리 입력 및 팀원 PM 평가 작성. 팀원 간 동료 평가 작성.
    *   *DB Point:* 다양한 평가 데이터가 `Evaluation` 테이블에 저장되는 과정 및 `Evaluation` 테이블과 다른 테이블 간의 조인(Join) 과정 시연.
*   **Scene 4: 경영진 대시보드 조회 (Executive View)**
    *   경영진 계정 접속. 전사 프로젝트 현황 및 특정 직원의 과거 참여 이력 조회.
    *   인센티브 산출을 위한 평가 점수 랭킹 뷰 시연 (사전 Import된 대량 데이터 활용).
    *   *DB Point:* 여러 테이블을 조인(Join)하고 GROUP BY 연산을 통해 복잡한 쿼리를 처리하는 과정 시연. 쿼리 최적화(Query Optimization) 개념을 언급하며 인덱스(Index) 활용의 중요성 강조.
